The request path should accept work, not become the work.

A public reference pipeline that separates document intake from variable-latency screening so retries, throughput spikes, OCR, persistence, and failure handling have explicit boundaries.

Case study boundary

This is a public reference implementation, not evidence of production traffic or a legal document-authenticity service. The screening logic is a plausibility check, and the case study calls out remaining reliability gaps rather than hiding them.

The engineering problem

Variable work does not belong inside a synchronous request budget.

Image handling, OCR, barcode parsing, and screening can take longer than a lightweight intake request should. Coupling all of that work to one HTTP transaction makes client latency, retries, and backend capacity part of the same failure domain.

The design instead treats acceptance and processing as separate reliability concerns. Intake validates and persists the submission, records searchable state, enqueues a job, and returns 202 Accepted. The worker can then process independently and expose progress through a status endpoint.

Reliability decisions

Each boundary changes what happens when one component slows down or fails.

01

Decouple acceptance from processing

The intake Lambda returns a submission identifier and status location after durable handoff instead of holding the client connection open for screening work.

02

Persist before processing

Submission metadata and binary input live in S3 while operational state lives in DynamoDB. A worker can reconstruct the job from durable inputs instead of depending on request memory.

03

Give retries a boundary

The work queue uses a 120-second visibility timeout for a worker configured with a 60-second Lambda timeout, plus a dead-letter queue after five receives.

04

Return partial batch failures

The worker reports failed SQS record identifiers through batchItemFailures, allowing successful records in the same invocation to stay complete while failed records are retried.

05

Separate permissions by role

Intake, worker, and status Lambdas use distinct IAM roles and narrow service actions: write/enqueue, read/process/update, and read status respectively.

06

Bound data and request growth

S3 lifecycle rules expire submissions and results on separate schedules, while API Gateway requires a key and applies configurable burst and rate limits.

Operational state

A queue tells you work exists. State tells you what happened to it.

Acceptance state

submissionId · status · submitted time · document type · source-data hints · object locations

Processing state

processed time · analysis score · review state · OCR source · barcode format · detected state · text length

Failure state

failed status · last update · error message · cumulative failure count

Searchable operations

DynamoDB secondary indexes organize submissions by status/update time and review status/processed time. That makes queue monitoring and analyst-oriented retrieval possible without scanning the full table.

Production hardening path

Reliability improves when the remaining ambiguity is made explicit.

  1. 1

    Close the enqueue gap

    Use a reconciler, transactional outbox pattern, or stream-driven handoff so durable acceptance cannot silently diverge from queue state.

  2. 2

    Make DLQ state visible

    Update terminal failure state, page on actionable backlog conditions, and provide replay tooling with bounded operator controls.

  3. 3

    Add service-level telemetry

    Measure queue age, processing latency, completion rate, failure rate, DLQ depth, and status-age distributions rather than relying on logs alone.

  4. 4

    Exercise failure paths

    Test throttling, worker timeout, duplicate delivery, malformed state, OCR failure, queue redrive, and replay before treating the system as production-ready.

Security & retention

Operational safety includes what the pipeline is allowed to retain and touch.

The Terraform configuration enables S3 versioning, server-side encryption, and a public-access block. Submission and result objects have separate configurable expiration periods. API Gateway requires a key and applies a usage plan rather than exposing an unrestricted endpoint.

IAM policy is split by execution role instead of giving every Lambda access to every pipeline operation. The worker can read submissions, write results, update status, and invoke Textract; the status function is limited to reading submission state.

What this demonstrates

Asynchrony is useful when it creates inspectable failure boundaries, not when it merely adds a queue.

This project demonstrates a serverless architecture where request latency, durable input, work scheduling, processing, status, retention, and retries are treated as separate concerns. The strongest evidence is not the number of AWS services; it is the explicit reasoning about where state lives and what remains recoverable after a component fails.

Explicit boundary: this public repository demonstrates the architecture and implementation shape. It does not claim measured production SLOs, production traffic scale, completed chaos testing, or legal authenticity verification.
