Distributed systems · OCI · reliability architecture

Kafka is only highly available when the recovery envelope is designed with the cluster.

A reference architecture for Apache Kafka on OCI that makes quorum, private networking, replication, capacity, observability, and operator behavior explicit instead of treating broker count as the definition of resilience.

Case study boundary

This repository is an architecture and operations scaffold. Terraform, provisioning automation, and failure-test validation remain intentionally marked as follow-up work rather than represented as production-ready.

The engineering problem

A cluster can have three brokers and still have a fragile failure model.

Kafka availability depends on more than process count. Controller quorum, replica placement, disk headroom, network bandwidth, DNS, certificates, client retry behavior, and the speed of replica recovery all contribute to the actual failure envelope.

The design therefore treats infrastructure, runtime state, and operator procedure as one system. The goal is not to hide Kafka behind a deployment button; it is to make the important reliability decisions inspectable and auditable.

Reliability decisions

Design choices that change the incident outcome.

01

Keep brokers private

Clients reach broker listeners through private connectivity and stable DNS. Network Security Groups separate client, replication, controller, metrics, and administrative traffic instead of exposing Kafka listeners broadly.

02

Protect quorum explicitly

Three KRaft voting members and failure-domain placement make controller loss a modeled event. Operations avoid taking additional controllers down while quorum is degraded.

03

Size for recovery, not normality

Disk and network capacity include headroom for replica rebuilds, partition movement, spikes, compaction, and growth. Recovery bandwidth is treated as an availability dependency.

04

Preserve durability semantics

Replication factor and min.insync.replicas are chosen together so acknowledged writes retain the intended durability guarantee during failures.

Capacity model

Storage exhaustion is an availability event.

retained_bytes ≈ingress_bytes_per_second × retention_seconds × replication_factor

The baseline is only the start. Production sizing also needs reserve for spikes, compaction, replica rebuilds, partition movement, filesystem overhead, and growth between reviews.

Operational alerts should fire before a volume becomes critical, with time-to-full calculated inside the response window rather than waiting for a static percentage threshold to become an incident.

Observability model

Page on durability and availability symptoms; ticket the slower capacity signals.

Cluster health

controller/quorum stability · offline partitions · under-replicated partitions · ISR churn · produce/fetch latency and errors

Host & JVM

disk latency · disk usage · network saturation · CPU · heap · garbage collection · file descriptors

Workload & capacity

bytes in/out · partition skew · consumer lag · retention growth · estimated time-to-full

Alerting principle

Do not page on every noisy metric. Page where durability or availability is plausibly threatened; route lower-urgency capacity signals to planned work.

Incident path

Diagnose the failure domain before changing the cluster.

  1. 1

    Scope the symptom

    Client-facing, replication, controller, or capacity? One broker/fault domain or cluster-wide?

  2. 2

    Preserve durability

    Avoid restarting healthy brokers or multiple controllers. Confirm remaining replicas still satisfy the intended durability threshold.

  3. 3

    Restore one failure at a time

    Repair the failed process, instance, disk, network path, or certificate state before introducing additional change.

  4. 4

    Observe recovery pressure

    Watch ISR recovery, network and disk saturation, leadership, client errors, and replica catch-up before proceeding.

  5. 5

    Close the loop

    Record impact and timing, compare recovery to SLO/runbook assumptions, and add reproducible failure tests where practical.

What this demonstrates

Principal-level systems thinking is mostly about making tradeoffs and failure boundaries explicit.

This project shows an approach to distributed infrastructure where networking, quorum, capacity, telemetry, security, recovery, and operator procedure are designed together. The useful artifact is not just the topology; it is the set of decisions that tells the next engineer what must remain true when something breaks.

Explicit boundary: this is a reference architecture and operations scaffold. It does not claim completed Terraform provisioning, automated Kafka installation, or validated production failure testing.
