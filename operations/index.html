Operations · incident response · observability

Start with the failure the operator can actually see.

Dashboards are useful only when they shorten the path from symptom to decision. My operating model is to identify user impact, locate the failure boundary, preserve ambiguous state, and choose the least-destructive recovery action that restores confidence.

Four operating rules

  1. 01
    Page on impactUrgency should follow availability, durability, or an expiring recovery window.
  2. 02
    Preserve uncertaintyA timeout is not proof that work failed.
  3. 03
    Prefer reversible recoveryStop, isolate, drain, or replay before reaching for destructive actions.
  4. 04
    Leave evidence behindLogs, status, decision records, and runbooks should make the next response faster.

Incident triage

Classify the ambiguity before choosing the recovery.

Different failures can produce similar symptoms. The first useful question is usually not “which metric is red?” but “what do we know happened, and what state might still be in motion?”

AWS · asynchronous work

Queue age is rising

Symptom
Oldest SQS message age remains above five minutes across two evaluation periods.
First checks
Worker Lambda errors, queue depth, recent deployment/configuration changes, and downstream processing health.
Recovery bias
Restore worker capacity or processing health before replaying anything. A DLQ message means normal retries were already exhausted.
Public evidence
The Terraform defines queue-age, worker-error, and DLQ alarms as separate operational signals.

OCI · Kafka

Cluster health is degrading

Symptom
Offline partitions, sustained under-replication, quorum instability, broker loss, or an approaching disk-exhaustion window.
First checks
Controller/quorum health, affected replicas, fault-domain concentration, disk/network headroom, client errors, and recovery throughput.
Recovery bias
Protect acknowledged-write durability first. Avoid moving more data until the cluster has enough recovery headroom to survive the intervention.
Public evidence
The reference architecture separates page-worthy availability/durability symptoms from lower-priority capacity signals.

OCI · Hadoop · SSH

The remote command timed out

Symptom
The function lost visibility before receiving a terminal remote exit status.
First checks
Determine whether failure occurred before SSH, during connection/authentication, or after command execution began; then correlate with Hadoop/YARN state.
Recovery bias
Do not automatically retry. The remote process may still be running, and the current interface has no idempotency key.
Public evidence
The runbook explicitly classifies a remote-command timeout as an unknown outcome.

OCI · lifecycle automation

A cleanup decision looks wrong

Symptom
A candidate resource appears eligible for mutation but the policy or ownership signal is incomplete or suspicious.
First checks
Management opt-in, protection policy, expiration source, action cap, dry-run output, and the structured reason trail.
Recovery bias
Fail closed. Preserve the resource and fix the policy signal rather than guessing that deletion is safe.
Public evidence
The janitor uses explicit ownership, reversible defaults, fail-closed parsing, and separate termination interlocks.

Alert design

Not every useful metric deserves a page.

Signals should map to an action and a response window. If an operator cannot say what changes because the alert fired now instead of tomorrow, it probably belongs in a dashboard or ticket.

ClassUse whenExamplesOperator action
PageAvailability, durability, or a recovery window is actively at risk.Offline Kafka partitions; quorum instability; DLQ arrivals for critical work; sustained service failure.Triage immediately, stabilize state, communicate impact.

Recovery decisions

The retry decision is part of the incident.

Retries are safe only when the operation is known not to have happened, or when repeating it is explicitly idempotent. Losing the response is not the same as losing the work.

Known pre-execution failureCorrect, then retry

Validation, missing configuration, authentication, or host-identity failures should be fixed before repeating the operation.

Known terminal failureUnderstand, then retry deliberately

A non-zero application exit can be safely reasoned about only after the underlying cause and side effects are understood.

Unknown outcomeObserve before retry

Timeouts after execution may create duplicate work. Check authoritative system state or a stable job identifier first.

Destructive actionPrefer a reversible stage

Stop, isolate, drain, quarantine, or dry-run before delete/terminate when the system allows it.

Evidence boundary

Public examples, not private incident history.

This page demonstrates an operating approach using behavior and runbooks that can be inspected in public repositories. It intentionally does not expose employer incident details, private dashboards, customer information, internal SLO targets, confidential architecture, or proprietary metrics.

The strongest claim here is methodological: define failure states precisely, connect signals to operator decisions, preserve ambiguous outcomes, and make recovery behavior reviewable.
