Architecture atlas · public engineering evidence

Four systems. Four different failure models.

A useful architecture diagram should explain more than which boxes talk to each other. These views focus on where state lives, where uncertainty enters, which controls limit the blast radius, and how the design is verified.

How I read a system

  1. 01

  2. 02
    Control boundaryWhere policy, throttling, isolation, or interlocks constrain behavior.
  3. 03
    Failure surfaceWhat can become unavailable, ambiguous, stale, or destructive.
  4. 04
    VerificationWhat proves the intended behavior before production depends on it.

01 · AWS · asynchronous processing

Accept quickly. Process durably. Keep status queryable.

The intake path separates request acceptance from document screening. That creates room for retries and throughput spikes without making API latency depend on every downstream step.

Data path
Failure surface
A long-running or failed screening job should not hold the request open or erase the accepted submission.
Control
API throttling, durable object storage, SQS buffering, a dead-letter path, and persisted status isolate slow or failed work from intake.
Verification
Unit tests mock S3/SQS interactions, a smoke path exercises the intake contract, and Terraform defines the deployed queue, storage, status table, Lambdas, and event mapping.
Boundary
The project is a plausibility screener and reference pipeline, not legal proof of document authenticity.

02 · OCI · distributed systems

Quorum is only one part of availability.

The Kafka design treats networking, storage headroom, recovery bandwidth, controller quorum, DNS, secrets, and client behavior as part of the same failure envelope.

Failure surface
A broker loss can become a durability or availability event if replicas, controller quorum, disk, network, or recovery capacity are already constrained.
Control
Private subnets, explicit NSG traffic classes, three voting members, replicated topics, fault-domain placement, dedicated storage, and time-bounded administration reduce correlated failure.
Verification
The operations plan calls for quorum checks, producer/consumer smoke tests, broker-loss tests, controller-loss tests, replica recovery observation, restart validation, and runbook exercises.
Boundary
The repository is a reference architecture and operations scaffold; it explicitly does not claim production readiness before provisioning and validation are completed.

03 · OCI · lifecycle automation

Destructive automation should fail closed.

The janitor does not infer that an old or quiet resource is disposable. It requires explicit ownership policy, validates expiration, caps actions, and separates stopping from termination.

Decision path
Failure surface
A false-positive cleanup decision is worse than a leaked temporary resource because it destroys state and can interrupt active work.
Control
Required opt-in tags, protection tags, dry-run default, stop-before-terminate, an explicit termination interlock, malformed-policy rejection, and a per-run action cap constrain blast radius.
Verification
Every evaluated resource can produce a structured decision record, so dry runs are inspectable audit output rather than opaque “would delete” logs.
Boundary
This is lifecycle enforcement for explicitly managed temporary compute, not an idle-resource detector or general cost optimizer.

04 · browser application · upstream uncertainty

Keep an undocumented dependency at the edge.

Sports Gamecast is static by design. The browser owns live-data fetches, parsing is defensive, refresh frequency follows game state, and deployment waits for mocked browser tests.

Failure surface
The upstream scoreboard endpoints are public but undocumented, so response shape and availability can change without a compatibility contract.
Control
Defensive parsing, retry messaging, state-aware polling, and a static deployment keep upstream uncertainty from becoming server-side operational complexity.
Verification
Playwright loads the scoreboard and Gamecast in Chromium against a mocked upstream feed; Pages deployment is gated on the browser smoke suite.
Boundary
The feed is an unofficial dependency. The design contains that risk; it cannot turn the endpoint into a supported API.

The common pattern

Make uncertainty explicit before automating around it.

Queues turn latency into durable work. Quorum design turns node loss into a recoverable event. Safety interlocks turn destructive automation into bounded policy. Defensive parsing turns an unstable dependency into a contained edge concern.

The tools differ. The engineering question is the same: what can fail, what state survives, and what proves recovery works?
