Operations case study · SRE tooling · observability

Correlate operational context without creating another hidden control plane.

Threatline is a local-first engineering operations workspace that connects work items, source changes, alerts, telemetry, runbooks, decisions, notes, and handoffs. The design question is not how many systems it can integrate. It is how to combine them without letting one provider failure, one credential boundary, or one ambiguous investigation result contaminate the rest of the operating workflow.

The operating problem

Incidents rarely live in one system.

Operational truth is usually fragmented across a work tracker, source control, monitoring tools, runbooks, local notes, and whatever an engineer remembers from the last handoff. The useful question is not “which dashboard has the answer?” It is “what changed, what is failing, who owns it, what evidence applies, and what should the next operator know?”

Threatline treats those systems as providers of context rather than replacing them as systems of record. External data is normalized behind provider boundaries, correlated around services and work, and surfaced through Today, Queue, Investigation, Daily Notes, and Handoff views.

Boundary: the current application is not a hardened multi-user Internet service, a hosted telemetry platform, or an autonomous remediation system. Its default trust boundary is a single trusted workstation user.

Observability integration

Useful context without pretending every signal means the same thing.

Grafana is deliberately link-first. Zabbix active problems and CloudWatch alarms can normalize into alert context. OpenTelemetry adds authenticated OTLP/HTTP traces, metrics, and logs with bounded local retention and service correlation.

The boundaries matter. CloudWatch is read-only and relies on the standard AWS credential chain rather than persisting access keys. OpenTelemetry summaries remain provider-local instead of leaking vendor payloads into the core domain. Telemetry errors are recent evidence; they are not automatically promoted into authoritative incident state.

That distinction lets the system correlate evidence while still preserving uncertainty.

Investigation semantics

Evidence review is not root-cause theater.

Bound

Put ceilings on collection

Provider collections, evidence records, persisted payload size, investigation windows, history count, and retention all have explicit limits.

Preserve

Save what was actually reviewed

Investigation runs persist workspace-scoped evidence snapshots so reopening a run shows the captured evidence, not whatever providers return today.

Expose

Keep gaps visible

Unavailable providers, clipped evidence, missing service mappings, and bounded collection are reported as limitations instead of being smoothed over.

Refuse

Do not invent certainty

The current evidence engine performs deterministic review only. Completion means the review ran without recorded gaps; it does not mean an incident recovered or root cause was established.

Design boundaries

The roadmap is not the shipped product.

Threatline documents stable seams for more providers, richer investigations, enterprise identity, remote operation, and remediation without representing those seams as existing capabilities.

The current public implementation intentionally keeps several lines bright: local-first rather than multi-tenant hosting; provider health rather than global success/failure; normalized context rather than vendor payloads in the core; evidence review rather than autonomous diagnosis; explicit mutation rather than background control.

Those boundaries are part of the architecture, not disclaimers added after the fact.

Inspectable evidence

What a reviewer can verify.

  • Organization-neutral operational domain objects and provider capability contracts.
  • Independent provider health behavior and failure isolation.
  • Jira and source-control context plus Grafana, Zabbix, CloudWatch, and OpenTelemetry integrations.
  • Workspace configuration and separate credential storage with diagnostic redaction.
  • Bounded investigation runs with durable evidence snapshots and explicit gaps.
  • Linux, macOS, Windows, fresh-install, Docker, performance, and release-consistency validation.
  • Documented security, observability, investigation, provider, architecture, and release boundaries.
