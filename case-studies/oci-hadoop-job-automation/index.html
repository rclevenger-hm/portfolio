Reliability case study · OCI · Hadoop · remote execution

The dangerous part of remote execution is not sending the command. It is knowing what happened afterward.

OCI Hadoop Job Automation submits validated Hadoop commands from an OCI Function over SSH. The reliability problem is to keep trust, time, retries, and failure state explicit when the remote system can continue doing work after the caller loses certainty.

The operating problem

A timeout is not proof that nothing happened.

A serverless wrapper around SSH can look straightforward: validate input, connect, run Hadoop, return stdout. Operationally, the hard part begins when a connection drops or a command exceeds the caller's timeout. The function may have lost visibility while the remote process continued.

That makes retry policy part of the architecture. Blindly resubmitting an ambiguous request can duplicate work, overwrite output, or turn a transient network problem into an application-level incident.

Boundary: the current implementation is intentionally synchronous and is suitable for short submission or management commands. It does not claim to provide a durable background-job control plane or real-time Hadoop status tracking.

Reliability controls

Control uncertainty before adding automation.

01

Validate first

Required request fields are checked before any SSH session or remote command is constructed.

02

Constrain command shape

Filesystem paths are shell-quoted and the Java job class is limited to an allowlisted character pattern.

03

Verify host identity

System known-hosts data is loaded and unknown SSH hosts are rejected rather than trusted automatically.

04

Bound network waits

Connection, banner, authentication, and remote command execution have explicit timeout ceilings.

05

Propagate failure clearly

Non-zero Hadoop exits and SSH/configuration failures return useful context rather than being flattened into generic success/failure.

06

Refuse unsafe retry assumptions

A remote-command timeout is treated as an unknown outcome until cluster state is checked.

Architecture boundary

The safe next design is asynchronous, not a longer timeout.

Submit

Return a stable identifier

Long-running work should be accepted and assigned an application or job identifier instead of holding the request open.

Persist

Store explicit state

Submission, running, terminal success, terminal failure, and unknown states should survive a function invocation.

Query

Separate status from submission

A status API removes the need to infer remote state from whether the original request connection survived.

Deduplicate

Add idempotency before automatic retry

Retry safety improves when duplicate submission can be detected instead of assumed away.

Inspectable evidence

What a reviewer can verify.

  • Python request validation and safe command construction.
  • SSH host-key verification and bounded connection/authentication timeouts.
  • Remote command timeout behavior and non-zero exit propagation.
  • Unit tests covering shell metacharacter quoting, invalid job-class rejection, missing fields, and unsupported control characters.
  • An operations runbook covering failure modes, incident triage, retry guidance, observability recommendations, and the asynchronous evolution path.
