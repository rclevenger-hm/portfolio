Reliability case study · browser application · CI/CD · GitHub Pages

An unreliable upstream feed should degrade the product, not redefine it.

Sports Gamecast is a static, multi-sport live scoreboard and Gamecast that consumes an undocumented public sports feed directly in the browser. The engineering problem is to keep live behavior useful when the upstream contract can change, while making releases deterministic enough to trust.

The operating problem

Live data creates two failure surfaces: the feed and the release.

The application has no server to normalize or cache upstream responses. Every visitor depends on a browser-side integration with a source that is useful but not a supported production API contract. That makes defensive parsing and visible retry behavior part of the user experience rather than implementation detail.

The second risk is change. A static site is operationally simple only if a deploy cannot silently break scoreboards, Gamecast rendering, or the browser scripts that assemble the experience.

Boundary: the project explicitly treats its sports data source as an undocumented dependency. The case study demonstrates how uncertainty is contained; it does not claim an upstream availability guarantee.

Reliability controls

Keep uncertainty at the edge and make release behavior repeatable.

01

Stay dependency-light

The runtime remains static HTML, CSS, and JavaScript, avoiding an application server and reducing the number of moving parts required to serve a live experience.

02

Parse defensively

Browser code expects upstream data to be incomplete or unavailable and presents retry behavior instead of assuming a stable response contract.

03

Poll by game state

Live games refresh aggressively while finished or inactive slates can back off, tying load and freshness to the state that actually matters.

04

Mock the dependency

Playwright smoke tests exercise the scoreboard and Gamecast against controlled sports responses so release validation does not depend on the live upstream service.

05

Gate deployment

GitHub Pages deployment depends on the test job. Pull requests validate without publishing, while successful non-PR runs can proceed to release.

06

Regenerate volatile data

Broadcast mappings are refreshed during deployment and validated before the static artifact is published, separating generated current data from hand-maintained source.

Operational tradeoffs

Static architecture removes servers, not responsibility.

Availability

Fewer owned components

No application server, database, or API credential layer is required to render the core live experience, reducing owned infrastructure and operational overhead.

Dependency risk

Upstream change remains real

The browser still relies on an external feed. The design contains that dependency but cannot turn an undocumented interface into a guaranteed service.

Validation

Determinism over live integration tests

Release tests use mocked responses so failures represent application regressions rather than temporary upstream availability.

Freshness

Generated data at deploy time

Broadcast metadata can be refreshed on the release path without adding a persistent backend solely to keep a static site current.

Inspectable evidence

What a reviewer can verify.

  • A static multi-sport scoreboard and Gamecast with live-state-aware refresh behavior.
  • Explicit documentation that the upstream sports endpoints are undocumented and may change.
  • Playwright browser tests run against mocked sports responses before deployment.
  • GitHub Actions separates pull-request validation from Pages deployment.
  • PWA asset validation, generated broadcast-data validation, and concurrency controls in the release workflow.
  • A scheduled workflow path that periodically exercises the same validation and release machinery.
