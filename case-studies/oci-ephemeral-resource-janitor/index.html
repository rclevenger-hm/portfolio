Reliability case study · OCI · safe automation

Automating resource cleanup without automating a bad day.

OCI Ephemeral Resource Janitor enforces lifecycle policy for infrastructure that is explicitly supposed to expire. The engineering problem is not deletion; it is proving that every destructive action is intentional, bounded, explainable, and recoverable.

The operating problem

“Old” is not the same thing as “safe to delete.”

Temporary infrastructure accumulates: developer sandboxes, CI workers, QA machines, demos, experiments, and troubleshooting hosts. A naive cleanup script can reduce waste while introducing a larger operational risk: it infers intent from age and turns one bad assumption into destructive change.

The janitor therefore answers a narrower question: which explicitly managed temporary resources have expired, and what lifecycle action is permitted by policy?

Boundary: this is not an idle-resource detector or general OCI cost optimizer. CPU, network, and utilization signals are not used to guess whether an unmanaged resource is safe to remove.

Safety architecture

Destructive automation earns permission in layers.

01

Explicit ownership

JanitorManaged=true is mandatory. Unmanaged resources are outside the system's authority.

02

Valid lifecycle

Expiration comes from an absolute deadline, per-resource TTL, or configured global TTL. Invalid values fail closed.

03

Protection check

DoNotCleanup=true overrides age and protects the resource from action.

04

Bounded action

Dry-run is default and only a capped number of eligible resources can be selected in one run.

05

Second interlock

Live termination requires an explicit action plus a separate allow_terminate control.

06

Two-phase delete

Termination normally requires the instance to have already been stopped on an earlier run.

Decision model

Policy before mutation.

Each evaluated instance ends with an explicit reason, making the dry-run output useful as an audit record rather than a vague “would delete” log.

Why this is SRE work

The code is secondary to the failure model.

Detect

Make policy state legible

Every resource receives an eligibility decision and reason, making unknown state visible instead of implicit.

Bound

Cap consequences

Opt-in ownership, dry-run defaults, protected tags, and per-run limits prevent an accidental broad sweep.

Recover

Prefer reversible change

Stopping before termination preserves a safer intermediate state and creates a natural review interval.

Transfer

Make policy operable by others

Environment variables, policy files, OCI Function payloads, structured reports, and tests make behavior inspectable and portable.

Inspectable evidence

What a reviewer can verify.

  • Python policy engine and OCI discovery/action path.
  • OCI Functions entrypoint and deployment manifest.
  • Tests covering policy precedence, opt-in and exclusion behavior, TTL/deadline parsing, action caps, termination interlocks, and handler semantics.
  • CI coverage across Python 3.11 and 3.12.
  • Structured JSON reporting with scanned, eligible, selected, limited, and reason-count summaries.
